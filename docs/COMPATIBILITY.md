# Compatibility

You are here because a build failed with:

```
Additive-only contract violation in :<module> (docs/COMPATIBILITY.md).
These published signatures were removed or changed:
  - <signature>
```

or because `verify-kotlin-metadata.sh` printed `FAIL <module> emits metadata mv=...`. This document
explains both gates, plus the toolchain and language-version constraints that make them necessary.
The gates themselves live in `build-logic/src/main/kotlin/sdkbase.abi.gradle.kts`,
`build-logic/src/main/kotlin/sdkbase.abi.jvm.gradle.kts`,
`build-logic/src/main/kotlin/sdkbase/abi/AbiTasks.kt`, and `scripts/verify-kotlin-metadata.sh`. If
this document and the code ever disagree, trust the code.

## The additive-only ABI policy

Every published module (`gradle/module-topology.gradle.kts` → `publishedArtifacts`) carries a
committed baseline at `api/<module>.api`, generated by `apiDump` and checked by `apiCheck` (wired
into `check`). The policy is an asymmetry, not a "no changes" rule:

| Change | `apiCheck` result |
|---|---|
| Add a new public class, function, or member | **Passes**, with no need to re-run `apiDump` first |
| Remove a public signature | **Fails** |
| Change a public signature (return type, parameter type, etc. — its text no longer matches) | **Fails**, because to `apiCheck` a changed signature and a removed one look identical: the old line is gone from the current dump |

`ApiCheckTask` (`AbiTasks.kt`) implements exactly this asymmetry: it reads the committed baseline
and the freshly generated dump, and fails only on lines present in the baseline but absent from the
current dump. It never fails because the current dump has lines the baseline doesn't — that's what
makes additions free. This is the actual mechanism, not a policy statement layered on top of a
generic diff: read `ApiCheckTask.check()` if you want to see the whole rule, it's about 15 lines.

This asymmetry is exercised deliberately as part of building this gate: a placeholder function is
added and dumped (passes), a second function is added without a re-dump (still passes — the point of
the exercise), then a function is deleted (fails, quoting the removed signature), confirming the gate
actually fires rather than silently passing. Reproduce it yourself with any module before trusting a
change to this plugin:

```
./gradlew :sdk:platform:apiDump && ./gradlew :sdk:platform:apiCheck   # both succeed
# add a public function, do NOT re-dump
./gradlew :sdk:platform:apiCheck                                     # still succeeds — additions are free
# remove a public function
./gradlew :sdk:platform:apiCheck                                     # FAILS, names the removed signature
```

## Regenerating a baseline

```
./gradlew :<module>:apiDump
```

This overwrites `api/<module>.api` with the module's current release ABI and must be committed in
the same commit as the API change that caused it (`docs/CONTRIBUTING.md` states this as a rule, not
a suggestion).

Regenerating is **legitimate** when the diff is a genuine, reviewed addition — a new public
function, class, or overload you meant to ship. It is **covering up a break** when you run it
because `apiCheck` failed on a *removal or signature change* and re-dumping made the red build green
without anyone deciding that break was intentional. If a removal is a deliberate breaking change
held for a planned major version, `apiDump` is still the right command, but it must be paired with a
commit message that says so explicitly — never a silent "fix build" commit. `apiCheck`'s own failure
message says the same thing.

## Why the dump reads the release AAR's bytes, not compiler output

`GenerateApiDumpTask` extracts `classes.jar` from the actual `*-release.aar` (`GenerateJvmApiDumpTask`
does the equivalent for `:sdk:core`'s plain `.jar`, since it has no AAR wrapper) and runs `javap`
against the extracted `.class` files — not against the Kotlin compiler's own output before packaging.
This is deliberate: the AAR's bytes are literally what a consumer resolves from Maven Central, so
there is no path for the baseline to drift from what actually ships. A packaging step that
accidentally stripped or renamed a class would show up in this dump; it would not show up in a
diff of compiler output taken before packaging.

## Two caveats found in a real baseline

**Kotlin `internal`/`private` is not a JVM concept, and the dump now reads the real Kotlin
visibility instead of guessing from it.** The JVM has no access modifier matching Kotlin's
`internal`, and `private` on a companion-object member does not make the JVM field private either
— a top-level `internal const val`, a top-level `internal val`, and a `const val` inside a `private
companion object` (even one physically emitted onto the *outer* class, as `TAG`-style companion
constants are) all used to compile to a plain JVM-`public` member and appear in the dump exactly as
if they had been declared `public`. This bit three separate baselines before it was fixed (Tasks 3,
7 and 8), each time silently adding a declaration that was never really public API.

The fix is `kotlinPublicApiFilter()` (`build-logic/src/main/kotlin/sdkbase/abi/KotlinVisibility.kt`):
both dump tasks read each class's own `kotlin.Metadata` annotation (via `kotlin-metadata-jvm`) and
drop a member whose *real* Kotlin declaration was `internal`/`private`, in addition to the existing
`/internal/`-package and synthetic-member filters. This means the package convention below is no
longer load-bearing for correctness — Kotlin `internal`/`private` alone is now enough to keep a
declaration out of the dump, at any nesting level. Putting a declaration in an `internal` *package*
(a directory literally named `internal`, matching `.../otp/internal/`) is still good practice for a
human skimming the module's structure, and still keeps the whole class out of Dokka's rendered docs,
but it is no longer the only thing standing between a leak and the published contract.

**A default argument emits a synthetic overload, and it is recorded on purpose.** A Kotlin function
or constructor with a default argument compiles to two JVM members: the one you wrote, and a
synthetic `(..., int, kotlin.jvm.internal.DefaultConstructorMarker)` overload the Kotlin runtime
uses to dispatch calls that omit the default. `isMangledMember()` does **not** filter this one out —
it filters `$default(...)` bridge methods and `access$...` synthetics, but the
`DefaultConstructorMarker` overload survives into the baseline (see `platform.api`, e.g.
`AndroidSdkLogger(java.lang.String, boolean, int, kotlin.jvm.internal.DefaultConstructorMarker)`).
This is correct, not an oversight: a Java caller links against that overload directly, so removing
the Kotlin function's default argument later would remove that overload too — recording it means
`apiCheck` catches that as the breaking change it actually is for Java callers. Do not "clean up"
the baseline by hand-deleting these lines.

One place this overload is *not* kept: a companion or nested object's own constructor. Kotlin gives
every companion/`object` a JVM-`public` `(..., DefaultConstructorMarker)` constructor bridge
regardless of the real constructor's declared visibility — even a zero-argument `private companion
object` gets one. `kotlinPublicApiFilter()` reads the real declared constructor's Kotlin visibility
(always `private` for a companion/object — you cannot `new` one from Kotlin or Java) and drops the
bridge along with it. This is different from the `AndroidSdkLogger` case above only in *why* the
bridge exists: there, it dispatches a genuinely public constructor's default argument, and a real
caller depends on it; for a companion/object, nothing can ever call it (no caller can construct a
`DefaultConstructorMarker` to pass), so keeping it in the contract would protect nothing.

## A third caveat: Compose modules record compiler-generated lambda singletons

A Compose module's baseline contains entries like:

```
public final class ...otp.ui.ComposableSingletons$OtpScreenKt {
    public final Function3<...> getLambda$-1696491560$otp_ui_compose();
}
```

These are Compose compiler artifacts, not API anyone calls. They were tested rather than assumed:
changing the text inside an existing lambda, and adding a new composable call inside one, both left
every hash unchanged and `apiCheck` green — so ordinary UI edits do **not** churn the baseline.

The hashes are keyed on the composable group's identity, however, not on its content. Renaming the
enclosing file or function, or reordering the top-level composables in a file, can change them. So:

> If `apiCheck` fails on a Compose module and **every** removed signature it names belongs to a
> `ComposableSingletons$...` class, that is a false positive from a code move, not a broken contract.
> Re-dump, and say so in the commit message. If even one named signature is a real declaration of
> yours, treat it as a genuine break.

## Toolchain floor

| Tool | Version | Constraint |
|---|---|---|
| Gradle | 9.7.1 | AGP 9.4.1 requires Gradle **>= 9.6.0** |
| AGP | 9.4.1 | max supported `compileSdk` is 37 |
| Kotlin | 2.4.20 | raised from AGP's bundled 2.2.10, see below |
| `compileSdk` | 37 | |
| `minSdk` | 24 | |
| JDK toolchain | 17 | every module targets this via `jvmToolchain(17)` |
| JDK launcher | 21 | the Gradle daemon itself; the *toolchain* compiles against 17 regardless of the launcher |

Raising any of these is a compatibility decision, not a routine bump — reread this document, and in
particular the metadata floor section below, before doing so.

## AGP 9 rules

- **Never apply `org.jetbrains.kotlin.android`.** AGP 9 supplies Kotlin support itself (built-in
  Kotlin); applying the plugin explicitly fails the build with "The 'org.jetbrains.kotlin.android'
  plugin is no longer required for Kotlin support since AGP 9.0." Android library and application
  modules apply only `com.android.library` / `com.android.application`.
- **KGP is raised above AGP's bundled version via a root `buildscript` classpath entry**, not via any
  AGP setting:
  ```kotlin
  buildscript {
      repositories { google(); mavenCentral() }
      dependencies { classpath("org.jetbrains.kotlin:kotlin-gradle-plugin:2.4.20") }
  }
  ```
  Gradle resolves the conflict upward (AGP 9.4.1's own KGP 2.2.10 loses to this classpath entry, so
  the build actually runs on 2.4.20).
- **`android.builtInKotlin=false` is not used, and must not be used going forward** — it is the
  escape hatch back to a separately-applied Kotlin plugin, and it is **removed in AGP 10**. Anything
  relying on it now creates a forced migration later.
- **The Compose compiler plugin is still required** for any module with `buildFeatures.compose =
  true`, independent of built-in Kotlin — AGP 9's built-in Kotlin support does not include the
  Compose compiler. Apply `org.jetbrains.kotlin.plugin.compose` (`libs.plugins.compose.compiler`)
  wherever Compose is enabled; omitting it fails configuration with "the Compose Compiler Gradle
  plugin is required when compose is enabled."

## `-jvm-default`

`-Xjvm-default` no longer exists in this Kotlin version. The current flag is `-jvm-default`, and its
valid values are `enable`, `no-compatibility`, and `disable`; the old values `all` and
`all-compatibility` are invalid and fail compilation with "Unknown -jvm-default value" if used.
Published modules set `-jvm-default=enable` (`sdkbase.android.library.gradle.kts`,
`sdkbase.kotlin.jvm.gradle.kts`) specifically to keep the `DefaultImpls` compatibility bridge that
Java hosts link against — `no-compatibility` would compile cleanly but silently break any Java
caller depending on that bridge.

## The metadata floor, carefully

An **unpinned** Kotlin 2.4.20 toolchain emits Kotlin metadata `mv = 2.4.0` on every class. A host
project still on an older Kotlin version cannot read metadata newer than what its own compiler
understands, so shipping `mv = 2.4.0` would silently break consumption for any such host — with no
compile error on the SDK's own build to catch it.

Pinning `compilerOptions.languageVersion` and `apiVersion` to **either** `2.0` **or** `2.2` makes the
*same* 2.4.20 toolchain emit metadata `mv = 2.0.0` instead — the metadata binary format version does
not track `languageVersion` one-for-one, and both of these language versions happen to land on the
same format version.

**The floor is set to `2.2`, not `2.0`,** even though both emit the same `mv`, because
`languageVersion = 2.0` additionally emits:

```
w: Language version 2.0 is deprecated and its support will be removed in a future version of Kotlin
```

and this warning fails any build run with `-Psdkbase.warningsAsErrors=true` — which is how CI runs
(`sdkbase.warningsAsErrors=false` is the local default in `gradle.properties`). `2.2` emits the
identical `mv = 2.0.0` metadata with no such warning, so it is strictly better than `2.0` at zero
compatibility cost. The floor is declared once, as `kotlinMetadataFloor` in
`gradle/libs.versions.toml`, specifically so a project derived from this base can change it in one
place.

**Raising `kotlinMetadataFloor` above `2.2` in a way that changes the emitted `mv` is a breaking
change for consumers** — it can silently drop support for hosts on older Kotlin — and must ship with
a major version bump, not as an incidental part of an unrelated change.

`scripts/verify-kotlin-metadata.sh` gates this by unpacking every published release AAR's
`classes.jar`, running `javap -v -p` against each class, reading the `mv` pair out of the classfile's
attribute table, and failing if any class exceeds format version `2.0` (the script gates on the
*format version* ceiling `2.0`, not on the source-level `kotlinMetadataFloor` string, since those two
numbers are not the same axis — see the comment at the top of the script). It is **AAR-only**: it
walks `build/outputs/aar/*-release.aar`, so `:sdk:core` — a pure-Kotlin JVM module that produces a
plain `.jar` — is not covered by this script at all. `:sdk:core` still has `languageVersion`/
`apiVersion` pinned in `sdkbase.kotlin.jvm.gradle.kts`, but nothing currently re-verifies its emitted
metadata format the way this script does for AARs.

## `aarMetadata.minCompileSdk` / `minAgpVersion`

Every published Android library module sets:

```kotlin
aarMetadata {
    minCompileSdk = libs.versions.compileSdk.get().toInt()   // 37
    minAgpVersion = libs.versions.agp.get()                  // 9.4.1
}
```

This embeds a floor into the AAR itself: a consumer whose own `compileSdk` is below 37, or whose own
AGP is older than 9.4.1, fails at dependency resolution / build configuration time on their side,
with AGP reporting the AAR's declared requirement rather than an unrelated downstream compile error.
This repository has not captured the exact wording of that consumer-side failure — treat the
mechanism above as verified, not the literal error text a too-old consumer sees.
